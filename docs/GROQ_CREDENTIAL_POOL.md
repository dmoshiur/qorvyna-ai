# Groq credentials

Administrators with the existing system settings permission can add, disable and delete provider credentials in Admin → AI → Provider accounts. Environment variables support `GROQ_API_KEY`, numbered `_2`–`_8`, and `GROQ_API_KEYS`; use only authorized credentials. Stored keys use AES-256-GCM and a server-side key derived from `PROVIDER_SECRET_KEY` (fallbacks exist; see `.env.example`). Keep the encryption key stable and protected. Replacement requires adding the new credential and removing the old one. Deleting an application record does not revoke the upstream Groq key: revoke it in Groq separately. Admin views include only a last-four key hint, not the full secret.

Groq quotas are organization-scoped. Organization identity is not verified by the current data model, so all keys are conservatively grouped per model rather than treated as independent quota. Pooled chat calls now use a Firestore transaction to coordinate provider-reported remaining capacity and reset windows across application instances. Reservations decrement known capacity atomically; out-of-order responses only lower remaining or extend a reset. An unknown-quota bootstrap lease permits one discovery call per model at a time and expires after three minutes if a worker dies. The lease limits concurrency; it is not a claim about Groq's allowance. Failed or ambiguous requests are not refunded. A 429 creates a shared cooldown. No default provider quota is invented.

The coordinator is enabled by default in production and can be enabled in development with `QORVYNA_GROQ_SHARED_QUOTA=true`. Firestore failures fail closed for pooled chat and allow the orchestrator to try another provider. Explicitly setting the flag to `false` disables this protection and is unsafe for a multi-instance deployment. Configure optional Firestore TTL for `provider_quota_windows.expire_at`; the ledger treats expired windows as unknown even without cleanup. Only server code can access the records. Provider headers may be missing, delayed, shared across models or reflect requests outside this application; estimates and locally observed windows cannot guarantee that Groq will never return 429. Direct non-pooled adapters and other applications using the same organization do not participate. This is not verified organization identification, independent-organization support, actual billing or a substitute for Groq enforcement. No live Groq or Firestore emulator verification was performed.

Reported limits and reset times come from response headers. Dashboard usage counters are process-local approximations (some token counts are estimates) rather than a provider invoice or durable complete accounting. No secret or user prompt is required in the dashboard. Use provider billing/console for actual billing and quota.
