# Explicit pull-request merge — staged design

The repository owner may explicitly review and merge an open, non-draft same-repository PR from the existing GitHub panel. No background or automatic merge is permitted. The server requires the connected user's push permission and GitHub enforces branch protection, merge policy and its own permissions. Only the GitHub `merge` method is offered in this stage. Fork PRs, binary/unsupported or large PRs, and unavailable mergeability fail closed.

A bounded preview reads the PR and its file patches, then rechecks its head and base. It presents the exact SHAs and GitHub-provided patches as untrusted text. GitHub can omit or truncate patch detail even when present, so users must inspect the complete current PR on GitHub. The preview's expiring, one-use HMAC record is bound to user, repository, PR number, both SHAs and base branch. The user must explicitly approve and confirm the irreversible merge.

Before sending the merge, the server rechecks permission, PR state and both SHAs, then atomically consumes the review. GitHub's merge API accepts an expected **head SHA**, which prevents merging a different head. It does not offer an expected base SHA: a base update can race between preflight and merge. This limitation must be shown in the UI; never claim an atomic base check. An uncertain network result is not retried; the user must inspect PR status before further action. The server reports success only if GitHub returns `merged: true` with a valid merge SHA.

Authenticated CSRF-protected endpoints, per-user process-local limits, metadata-only audits, server-only Firestore review records, bounded bodies and provider calls are required. Firestore TTL cleanup is separately configured by an operator. This is mocked-only until a disposable GitHub repository is tested; production callback/branch protections are not verified. This feature must not merge this repository's PR as part of implementation or testing.
