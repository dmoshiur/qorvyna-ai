# MCP: narrowly scoped GitHub file reader

The official `@modelcontextprotocol/sdk` client and Streamable HTTP transport back the opt-in, user-operated GitHub MCP reader in Agent Studio. Set `QORVYNA_GITHUB_MCP_ENABLED=true` and restart the application only after assessing the integration, account permissions, guardian policy and provider terms. Configure the existing GitHub OAuth app and token encryption as documented in `GITHUB_INTEGRATION.md`. The connected user's encrypted GitHub credential stays server-side; the token is sent only to GitHub's fixed `https://api.githubcopilot.com/mcp/` endpoint. OAuth scope/provider entitlement and GitHub MCP service access must be tested against that actual deployment. There has been **no live authenticated MCP verification**.

One operation, `get_file_contents`, is allowed. The user enters owner, repository, path and optional ref; each call requires a clear confirmation and existing user/tool/exact-argument-bound, single-use approval. Backend rules separately check age and require an approved **guardian** consent record for users under 18; unknown/invalid age fails closed. Existing account-level GitHub permissions and GitHub's API remain authoritative. The tool is not model-callable: retrieved content is displayed as untrusted plain text, not sent to a model or treated as instructions. Results are bounded and truncated; non-text MCP content fails honestly. GitHub may return directory listings, metadata or encoded binary as text; the application does not verify that a text result is a file or decode it. Explicit provider settings, tools, approval UI, route/session CSRF, device scopes, and audit events are independently enforced. Auditing is currently best effort, not tamper-proof. The gateway rate limit is process-local.

Endpoint is fixed HTTPS; arbitrary hosts, redirects, arbitrary MCP tools, discovery-driven execution, stdio, shell and general HTTP are not offered. Response bytes and time are bounded; only text tool results are accepted. Protocol execution is covered by mock transport tests using the real SDK, not an external service. The connector uses an existing OAuth token, not a provider-specific least-privilege MCP token; read permissions may cover private repositories. It does not inspect GitHub account age or establish whether an account or token is authorized for the remote service, and guardian approval is not proof of external-provider compliance. The system cannot categorically prevent malicious instructions appearing in displayed text; keep it out of model context.

The governed MCP connector registry (`src/lib/server/mcp/registry.ts` and `/api/mcp/connectors`) exposes two live, ownership-enforced read connectors (`workspace_projects` for owned QORVYNA project listings/files and `github_mcp` when `QORVYNA_GITHUB_MCP_ENABLED=true` and user OAuth is connected) while reporting `google_drive_mcp` and `gmail_mcp` honestly as `not_configured` until Google OAuth provider verification and guardian consent scopes are configured. No placeholder integration reports success.

The official GitHub MCP repository tool snapshot for `get_file_contents` was inspected on 2026-11-25 for its name and input fields; provider behavior and permissions remain unverified.
