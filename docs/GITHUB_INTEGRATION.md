# GitHub integration

The existing OAuth flow requests `read:user user:email repo`; it binds random state to the signed-in user, validates the return path, exchanges the code server-side and stores the token AES-256-GCM encrypted in `github_connections/{uid}`. Status validates `/user`; disconnect removes the stored connection but does **not** revoke the grant at GitHub. Users should also revoke it in GitHub settings. Reconnect through Agent chat. Existing legacy cookie names are intentionally retained.

The project workspace's GitHub panel supports selecting a writable repository, branch and text files, then **Compare with GitHub**. It reads the branch HEAD, walks its immutable Git tree, and displays the remote and staged text side by side for each selected path. It reports new, changed and unchanged files; it does not display deletions or calculate a line-by-line patch. Binary, executable, symlink, unsupported or oversized remote files fail closed; binary workspace assets are not selected for push. Individual paths can be deselected.

The server validates the files and issues an HMAC-signed review token bound to user, repository, branch, HEAD and file-content hashes, expiring in ten minutes. It stores only review metadata and digests in server-only `github_push_reviews`. The user must explicitly check the review box and confirm the push in the UI. At push the server verifies the token, rechecks push permission and HEAD, transactionally consumes the review once, then calls GitHub GraphQL `createCommitOnBranch` with `expectedHeadOid`. GitHub atomically rejects a stale HEAD, including changes between preflight and commit, and enforces branch protection. A network failure after sending a mutation can have an unknown result: check GitHub before trying again. Failed or consumed reviews require a new comparison.

Preview is limited to 40 files, 300 KB per file and 700 KB staged/remote totals; request and upstream response bodies are bounded and per-user preview/push limits are process-local. Existing file modes other than regular `100644` are rejected. The review screen renders untrusted repository content as text and never sends it to an AI. Environment files, duplicate paths and obvious private-key material are rejected, but this is not a comprehensive secret scanner. Audit records contain repository, branch and outcome, not file contents or tokens. Configure Firestore TTL on `github_push_reviews.expire_at` and `github_oauth_states.expire_at` if desired; no TTL policy is automatically enabled. Expiration is enforced in application code even without TTL; cleanup otherwise needs an operator-managed policy. Server rules deny browser access to these records.

## Limited import from the reviewed comparison

In a project workspace, the same comparison offers **Import reviewed remote files** as a separate action with its own approval and confirmation. It replaces only selected, changed, existing text files with the displayed remote versions at the listed immutable commit. This is an explicit snapshot import, not a merge: remote-only paths, deletions, binaries and directory browsing are not included. It currently requires a writable repository because it reuses the push comparison. It does not check whether GitHub HEAD moved after the comparison; the user is importing the displayed commit, not automatically the latest branch. Compare again to obtain a newer snapshot.

The workspace blocks import while browser edits are unsaved or a save is in progress/error. The server checks project ownership and atomically applies all selected files only at the reviewed project revision, with a pre-import snapshot in the same transaction. Concurrent project changes cause a conflict rather than overwrite; unrelated files are retained. The owner can restore the prior snapshot from the Assets tab. A lost response has an unknown outcome: inspect the workspace and snapshots before retrying. Limits include 40 files, 200 KiB per project text file and 700 KB imported content total. A project too large for a Firestore transaction fails without a partial import. Content is untrusted and may execute if the user opens a project preview; neither the comparison nor import sends it to an AI. The UI approval is not a cryptographic proof of human review: the project owner can already edit their own files through RPC.

The token proves the reviewed snapshot was generated for this user; it cannot prove a human read it. Repository access remains bounded by the connected GitHub credential. This is a comparison, guarded push, and limited snapshot import, not general two-way synchronization or conflict resolution.
## Reviewed pull request creation

The project GitHub panel offers same-repository PR creation from the selected source branch to a user-specified base branch. It compares immutable source and base SHAs, displays GitHub-provided text patches and metadata, and requires a separate approval and confirmation. This does **not** merge or modify files. It requires an explicitly writable repository and the connected GitHub account must also have permission to create a pull request. Creating PRs from forks, branch creation and formal PR reviews are not supported.

The signed ten-minute review is bound to user, repository, both branch names and SHAs, title and description, with server-only one-use `github_pr_reviews` metadata. It is consumed transactionally before sending the GitHub creation request. Configure Firestore TTL for `github_pr_reviews.expire_at` if desired; expiry is enforced even without TTL. The preflight rejects changed branch heads. GitHub's API accepts branch names, not expected SHAs: branches may move between the preflight and PR creation, and PRs track branches afterward. There is no atomic guarantee that a created PR still matches the comparison. Always inspect the actual PR before merging. On a timeout or other uncertain outcome, check GitHub for an existing PR before retrying.

The comparison rejects detectable missing patches, 300 or more files, more than 100 commits, and oversized responses, but GitHub can omit or truncate patch details without an explicit flag. It is therefore not a guarantee of a complete diff; users must verify on GitHub. PR content is untrusted, rendered as text, and never sent to AI. No merge or automatic retry is performed. Tests mock GitHub; this workflow has not been live verified. See [GITHUB_PR_REVIEW_SPEC.md](GITHUB_PR_REVIEW_SPEC.md).

## Read-only PR browsing and inspection

The same panel can load the selected repository's open and closed PRs, newest updates first, and inspect their metadata, descriptions and changed-file patches. It uses the user's existing GitHub credential; no repository content is sent to AI. Listing is limited to ten pages of 20 PRs and inspection to ten pages of 20 files. The repository selector currently lists writable repositories only. The UI labels missing/binary and locally truncated patches, while GitHub may also omit or truncate details without a marker. Descriptions are clipped at 5,000 characters and patches at 20,000 characters per file; the upstream response is bounded. User content renders as text.

Each file page is read between two PR metadata requests and rejected if the head, base, state or update timestamp changes between them. This is **not** a frozen snapshot: changes can occur after the check or between pages. Always review the current full PR on GitHub before any merge. Browsing alone performs no PR review submission or merge, and has only been tested with mocked GitHub responses. Reads use per-process rate limits and best-effort metadata-only audit events.

## Explicit PR merge

An eligible open, non-draft same-repository PR offers a **separate** merge review. The user loads a fresh preview, inspects GitHub-provided text patches, explicitly checks approval and confirms the irreversible action. It uses GitHub's merge-commit method only; no automatic merge or retry is performed. Fork PRs, missing patches, binary files, more than 100 changed files, or unknown/false GitHub mergeability fail closed. GitHub may omit or truncate patch detail without an explicit marker, so users must inspect the complete current PR on GitHub before approving.

The server binds a ten-minute, one-use signed review to user, repository, PR number, base branch and both SHAs. It verifies the connected account's explicit push permission and rechecks PR state and SHAs, then consumes the server-only `github_merge_reviews` record before calling GitHub. GitHub atomically verifies the **head SHA**, applies branch protection and its own permissions, but its merge API does not accept an expected base SHA. The base can move between our preflight and the GitHub merge; the UI warns about this race. If a response is lost or uncertain, inspect the PR on GitHub before doing anything else. A success message requires GitHub to return `merged: true` and a merge SHA. The token cannot prove that a human read the review.

Configure Firestore TTL on `github_merge_reviews.expire_at` if desired; expiry is enforced independently of cleanup. PR content is untrusted text and is not sent to AI. Tests mock GitHub and Firestore; the feature, OAuth permissions and branch protection have **not** been live verified. See [GITHUB_PR_MERGE_SPEC.md](GITHUB_PR_MERGE_SPEC.md).

## Deployment checklist

1. Verify the actual deployed HTTPS origin, DNS, TLS and routing. The requested public origin is `https://qorvyna.online`, but this checkout retains old host defaults; no live host was verified. Do not change a working deployment blindly.
2. Set `NEXT_PUBLIC_APP_URL` to the actual origin at build and runtime and `GITHUB_OAUTH_CALLBACK_URL` to exactly `<origin>/api/github/callback`. For the requested origin this is `https://qorvyna.online/api/github/callback`.
3. Register the identical callback in the GitHub OAuth App and add the active domain in Firebase Authentication authorized domains. Configure `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` and a strong stable `GITHUB_TOKEN_ENCRYPTION_KEY` in the server secret store.
4. Test signed-in connect, deny, wrong/expired state, changed session, status, reconnect, disconnect and an explicitly reviewed push to a disposable repo. Change the branch after comparison and confirm expected-HEAD rejection; test a second simultaneous push and verify the review is consumed once. Do not use a real production repository for initial testing.

The callback, comparison and push were tested with mocks only; the GraphQL mutation has not been exercised against live GitHub in this checkout. General repository browsing, full pull/sync and conflict resolution, branch creation, formal PR reviews, fine-grained permissions and upstream revocation are not implemented. A GitHub App with installation-scoped repository permissions could reduce the broad OAuth scope, but requires app registration, installation and token lifecycle, migration/consent UX, webhook verification and separate authorization tests before adoption; do not remove OAuth until migration is verified.
